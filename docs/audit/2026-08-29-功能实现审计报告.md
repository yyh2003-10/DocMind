# DocMind 功能业务实现情况审查报告

> 审查日期：2026-08-29
> 审查范围：全量（Python 后端 + WPF 客户端 + CLI + MCP），核心链路优先
> 审查基线：**当前工作区现状**（含大量未提交改动），非 HEAD 提交版本
> 审查方法：三层对账 —— 代码实况（Inventory）↔ 文档承诺（Docs）↔ 运行事实（Runtime）

## 一、审查结论速览

| 维度 | 结论 | 说明 |
|---|---|---|
| **核心链路** | ✅ **真实可用** | 摄入→分块→嵌入→存储→检索→RAG 全链路实测跑通，非桩实现 |
| **死链** | ✅ **0 条** | 客户端 39 个请求路径全部命中后端路由，无调用不存在的接口 |
| **UI 空壳** | ✅ **0 个** | 11 个 ViewModel 的 131 个 `[RelayCommand]` 逐个核查，均有真实业务 |
| **假数据桩** | ✅ **无** | graph/extract、creative/export、curate、quality 均为真实实现 |
| **测试健康度** | ⚠️ **修复后全绿** | Python 306 通过 / 0 失败（修复前 1 红）；WPF 200 通过 / 0 失败 |
| **接口冒烟** | ✅ **19 通过 / 0 失败** | 数据隔离到临时库，覆盖 24 个端点 |
| **文档同步** | ❌ **严重滞后** | MCP 工具数三方口径不一（7/11/12 vs 实际 15）；测试基线写 47 实际 200 |
| **能力埋没** | ⚠️ **7 个端点未接通 UI** | 其中 `/v1/curate`（AI 知识库整理）是 AGENTS.md 主推能力 |
| **核心卖点** | ⚠️ **有缺口** | 混合检索 BM25 对 <3 字符查询词静默失效（详见 AUD-003） |

**总体判断**：软件**不是 PPT 工程**，主体功能扎实可用、无死链无空壳。主要问题集中在三处——
① **短查询词下 BM25 失效**削弱了"双引擎混合检索"这一核心卖点；
② **7 个已实现后端能力未接通客户端 UI**（尤其 `curate`）造成投入浪费；
③ **文档严重滞后于代码**，对外承诺与内部口径互相矛盾。

## 五、缺陷清单

等级定义：**P0** 崩溃/数据错乱/核心链路不通；**P1** 功能不可用或结果与预期显著不符；**P2** 体验/一致性/文档问题。

### P0

| ID | 模块 | 位置 | 现象与影响 | 状态 |
|---|---|---|---|---|
| AUD-001 | WPF 对话页 | `ChatViewModel.cs:1862-1871` | **切换会话不取消进行中的流式请求**。旧流收尾时 `_chatId` 被旧会话 id 覆盖（:2741），随后 `LoadSessionsAsync(selectChatId:_chatId)`（:2755）重置 `SelectedSession`，**把用户刚选中的会话顶掉**，造成会话错乱。同类的 `Clear()`(:2908) 与 `DeleteSessionAsync`(:2938) 都有 `_cts?.Cancel()`，唯独切换路径遗漏 | ✅ **已修复** |
| AUD-002 | LLM 流式 | `core/llm/base.py:357-362`（原） | `with ThreadPoolExecutor(...)` 退出时 `shutdown(wait=True)`，若生产者线程卡在网络读上，消费循环**永久阻塞**、`rag_answer_stream` 不返回。断连/超时场景下前端只能干等（用户停止生成或切走后，后端线程仍挂着） | ✅ **已修复** |

### P1

| ID | 模块 | 位置 | 现象与影响 | 建议 |
|---|---|---|---|---|
| AUD-003 | **混合检索** | `core/store/sqlite_vec.py:95-129` + `_FTS_SQL:242-247` | **BM25 对 <3 字符查询词静默失效**。`bm25_index` 用 `trigram` 分词器，只能匹配 ≥3 字符的连续子串；`_build_fts5_match` 对短词回退为前缀 `"词*"`，而 trigram 索引不支持前缀查询 → 2 字中文词（"气缸"、"电机"、"电源"）与 2 字符英文缩写（"IP"、"5A"）**BM25 完全不召回**，混合检索退化为纯向量检索。实测：`MATCH "伺服驱动器"` 命中 1.47 分；`MATCH "气缸"` **返回 0 行**（文档中明确含"气缸缸径"）。这是 README 主推的"向量+BM25 双引擎"卖点的实质缺口 | 对短词改用 `LIKE '%词%'` 补充召回，或换用支持 bigram 的分词方案（如 jieba 预分词 + `unicode61`）；至少应在 `stats.degraded_reason` 中上报，避免静默 |
| AUD-004 | 会话存储 | `chat_store.py:67-71` | `_connect()` **缺 `journal_mode=WAL` 与 `busy_timeout`**，与 `sqlite_vec.py:292-296`、`graph_store.py:55-58` 不一致，并发写会话时易瞬间 `SQLITE_BUSY` | ✅ **已修复**（补 WAL + `busy_timeout=10000`） |
| AUD-005 | SSE 流式 | `server/http.py:1947-1949` | `asyncio.run_coroutine_threadsafe(queue.put(...)).result()` **无 timeout**，且 `Queue()` 无 `maxsize`（零背压）。event loop 关闭时工作线程永久阻塞 → 线程泄漏 | 加 `maxsize` 背压与 `.result(timeout=...)` 兜底 |
| AUD-006 | SSE 流式 | `server/http.py:1972-1978` | **无全局时长上限**：15s 空闲仅发心跳并 `continue`，无连续心跳次数上限。后端卡死则流无限持续 | 加最大时长或最大心跳次数上限 |
| AUD-007 | WPF 流式 | `Doc2kbApiService.cs:207` | `reader.ReadLineAsync()` **未传 `CancellationToken`**；且 `HttpCompletionOption.ResponseHeadersRead` 使 `HttpClient.Timeout` 不覆盖 body 读取。后端每 15s 心跳续命 → 后端卡在 LLM 调用时 **UI 永久转圈**；用户点"停止"最多延迟一个心跳周期（15s） | 传入 `ct` 并加空闲超时兜底 |
| AUD-008 | 多轮历史 | `core/rag.py:260` 与 `:287` | user 与 assistant **两次独立事务**落库（`chat_store.py:143` 每次各开事务）。assistant 写失败会留下孤儿 user 轮；并发下同 chat_id 两请求可交错为 `A_user,B_user,A_asst,B_asst`，而 `get_history` 按 id 升序取回 → **上下文错序** | 合并为单事务；或对同 chat_id 加写入串行化 |
| AUD-009 | 测试 | `tests/test_llm_providers.py:270`（原） | `test_manual_toml_api_key_still_loadable` 断言手写 toml 的 `llm_api_key` 可被回读，与 1.1 起的安全设计（`config.py:255-260` 明确不再回读敏感字段）**直接冲突**，且与同文件上一用例（断言 `llm_api_key not in content`）自相矛盾 → **测试红**。属测试过期，非生产代码缺陷 | ✅ **已修复**（改为断言新安全行为） |
| AUD-010 | 知识图谱 | `GraphView.xaml.cs:314` + `:319` ↔ `GraphTemplate.html:585-589` | **图谱数据双通道重复渲染**：`InjectGraphJson` 同时走 `PostWebMessageAsJson`（通道1）与 `window.renderGraph(...)`（通道2），而 HTML 的 message 监听器收到通道1 消息后**又调用一次 `renderGraph`** → 每份数据 `initFluidWaterSphereGraph` 执行两遍（重复初始化、动画状态重置、性能浪费） | 二选一保留（建议保留 `PostWebMessageAsJson`，其在注释中标为"安全高效"），删除冗余通道 |
