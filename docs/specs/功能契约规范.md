# 规格：DocMind 功能契约规范（每个功能可完成什么 + 过程闭环）

> 状态：`ready-for-agent`
> 生成自：规范选型调研（2026-09-09）+ 缺陷对账（`fix-ux-configuration-deficiencies.md` C/F/W/E 共 19 项、`fix-architecture-deficiencies.md` P0–P3）
> 前置约束：**目标用户是对外发布的普通用户**（非技术背景）。本规范的目标不是"代码写得规范"，而是**用户能不能走完整条任务**。
> 与前两份 spec 的关系：`fix-ux-*` / `fix-architecture-*` 是**缺陷导向**（先出问题再修）；本文档是**事前契约**（开工前填完，填不出来不许写代码）。

---

## Problem Statement

DocMind 现有规格全部以缺陷为单位组织。这导致一个结构性盲区：**一个功能可以"实现了"但"用户走不完"**——它有代码、有测试、有文档，但用户执行到某一步就卡住，且软件不告诉他下一步该做什么。

已有证据（全部来自本项目自己的审查记录，非推测）：

| 类型 | 实例 | 表现 |
|---|---|---|
| 取消不闭环 | 导入（W1） | 取消只停前端轮询，**后端继续跑**。半成品已入库但用户以为取消了 |
| 前置条件不检查 | 对话（F2）、抽取图谱 | 无 LLM 配置时**发消息/点按钮才报错**，而非事前引导 |
| 成功不可判 | 设置保存（C1–C2） | 三种生效语义并存（实时/重启后端/下条消息），用户无法知道"保存是否生效" |
| 失败无出路 | 后端离线（E1–E3） | 各页零散报错，**无统一的检测→恢复动作**，兜底指向后端日志 |
| 空态与错误混同 | 搜索 | "无匹配结果"不区分**空库**（需导入）与**无命中**（需换词） |
| 隐性语义 | API Key（C3） | "留空=保留原值，须点清除才真清除"，用户无此心智模型 |
| 注释与实现漂移 | `ToolCallResilience.SearchWithHealingAsync` | 注释称空结果放宽阈值重试，实现只在异常时调整 |

共同根因：**这些环节在开发时不产生报错，所以没人测、没人写、没人 review。**

## Solution

每个功能在开工前必须产出一份**功能契约**，包含五部分：

```
功能契约 = 前置条件 + 输入契约 + 状态机 + 4 个出口 + 完成判据
```

**第 0 步 · 前置条件**：这个功能需要什么才可用？（后端在线？模型已配？Key 有效？库非空？）
不满足时**禁止报错**，必须给一个「去满足它」的动作按钮（复用 `NavigateToSettingsRequested` 范式）。

**4 个出口，一个都不许缺**：

| 出口 | 必答问题 | 禁止做法 |
|---|---|---|
| 成功 | 用户看到什么？**完成判据是可观测的什么？** | 只更新数据库、UI 无反馈 |
| 失败 | 用户**下一步点哪里**？（要动作，不是报错文案） | 抛原始异常给 UI |
| 取消 | 取消后系统停在什么状态？**半成品清不清？** | 只停前端轮询 |
| 空态 | 无数据时是"空态"还是"错误"？两者文案与出路**必须不同** | 空库与无命中同一句"无匹配结果" |

**诊断口诀**（PR review 时逐句问，答不出即不合并）：

> 做完用户看到什么？做失败用户下一步点哪里？取消后系统留了个什么状态？没数据时显示的是空态还是错误？

**取消出口特别说明**：这是最容易被漏掉的出口——因为取消不产生报错，开发时无人测。规范要求：
1. 取消必须是**对任务对象的操作**，不是前端停轮询。
2. 任务必须有独立生命周期对象，可查询状态（`idle / running / cancelling / cancelled / succeeded / failed`）。
3. 取消后必须显式声明残留状态的处理策略（已入库的分块删不删？半成品集合清不清？），并在契约里写出来。

## 功能契约模板（复制填空）

```markdown
### 功能：{名称}

**能完成的任务**（一句话，用户视角）：
例：把我选的文档导入知识库，之后能搜索到。

**不能完成的事**（边界，防范围蔓延）：
例：不解析受密码保护的文件；不自动重导入已存在文件（除非勾选强制）。

**前置条件**：{需要什么} → 不满足时：{动作按钮文案 + 跳转}

**输入契约**：{类型 / 约束 / 非法输入的反馈方式}

**状态机**：idle → running → (cancelling → cancelled) | succeeded | failed

**4 个出口**
- ✅ 成功：{用户看到什么}｜完成判据：{可观测条件}
- ❌ 失败：{用户下一步点哪里}
- ⏹ 取消：{系统残留状态 + 清理策略}
- ∅ 空态：{文案} ｜ {出路动作}

**恢复路径**：失败后软件如何自己回到可用状态（如离线横幅的重测/重启）

**可执行测试**（Given/When/Then，至少覆盖 4 个出口各一条）
```

## 示例：导入功能的完整契约（按本规范填写的样板）

- **能完成的任务**：把我选的文件或目录导入知识库，之后自然语言搜索能命中。
- **不能完成**：不解析加密文件；不导入单个 >500MB 的文件；不重复导入同 MD5 文件（除非勾选强制重新摄入）。
- **前置条件**：后端在线 + 嵌入模型已加载 → 不满足时：「后端未连接，去启动」/「嵌入模型加载失败，去设置页查看」。
- **输入契约**：文件路径或目录；单文件超 500MB 时该文件**跳过并计入跳过数**，不阻断整批。
- **状态机**：`idle → hashing → running → (cancelling → cancelled) | succeeded | partially_succeeded | failed`
- **4 个出口**：
  - ✅ 成功：进度条走满 + 「已导入 N 篇 / 跳过 M 篇」+ 自动跳到搜索页。完成判据：`IngestResult.ingested` 非空且后端 `/v1/stats` 文档数增加。
  - ❌ 失败：逐文件列出失败原因（人话，不含堆栈）+ 「重试失败项」按钮。
  - ⏹ 取消：**调后端取消端点**（不是停轮询）→ 已入库分块**保留**（可用且可搜索）→ 显示「已取消，前 N 篇已导入」。
    - 实测现状（2026-09-09 核实）：**真取消主路径已实现** —— 后端 `DELETE /v1/jobs/{job_id}` 置 `cancel_event` 并置 `status=cancelled`，WPF `ImportViewModel.CancelImport()` 调 `CancelJobAsync`。
    - 剩余缺口两条，见 FC-01a / FC-01b。
  - ∅ 空态：未选文件时导入按钮禁用 + 占位说明拖拽区域。
- **可执行测试**：`Given 导入进行中 When 用户取消 Then 后端任务状态 == cancelled AND 已完成文件可搜索 AND 未完成文件未入库`

## 缺陷对账：现有 6 个功能的闭环缺口

按上表模板逐个检查。初版判为 8 个破口，**实测校准后为 5 个真实缺口 + 3 条已实现**（编号 FC-01a…FC-08，可入 issue 追踪）：

> ⚠️ 本表已于 2026-09-09 用代码实测校准。初版把 FC-01 判为"后端无取消端点"、把 FC-02/FC-06 判为完全未做——**均为误判**，实测已实现。下表按实测重写。这正是本文档要治的"文档与代码漂移"，此处留痕作为反面样例。

| # | 功能 | 破的出口 | 实测现状与真实剩余缺口 | 归属 |
|---|---|---|---|---|
| FC-01a | 导入 | 取消（粒度） | ✅ 真取消主路径已实现（后端 `DELETE /v1/jobs/{id}` + WPF `CancelJobAsync`）。❌ 但 `cancel_event` 只在 progress 回调点检查（`http.py:1962` `_check_and_update_progress`），**单文件解析/OCR 中不响应**，大 PDF 可能长时间无法取消 | 新增 P0 |

| FC-03 | 对话 | 失败 | ❌ 后端不可达时对话页仍单独报错，未走全局离线横幅 | `fix-ux` 批次 4 / E1 |

注：原独立的 `alphagov/gds-patterns` 仓库已并入 govuk-design-system 的 `src/patterns`。

### 第 2 层 · API 合约 → `zalando/restful-api-guidelines`（CC-BY-4.0，可自由引用改写）

3,244 ⭐。23 章，每条为 `[#100]` 编号 + **RFC 2119 {MUST}/{SHOULD}/{MAY} 标签**——这是"规范"应有的形态。

规则 `[#100] {MUST} follow API first principle`：先定义 API（OpenAPI 单一源），再写实现，并用 linter 自动校验。**这正是 `fix-architecture-deficiencies.md` P0/P1 的处方**（`IngestResult` 字段名漂移、`HealthStatus` 含后端不返回字段、MCP 与 HTTP 质量报告字段不一致、`docs/api.md` 与实现不符）。

可直接抄章节：`general-guidelines`、`http-status-codes-and-errors`、`pagination`、`deprecation`、`compatibility`。
**不用抄**：`events`、`hyper-media`（本项目只有一个本地进程，非多服务）。

### 第 3 层 · 代码结构 → `dennisdoomen/CSharpGuidelines`（776 ⭐）+ `bkoelman/CSharpGuidelinesAnalyzer`（Apache-2.0）

价值在于 analyzer 能把规则**变成编译期诊断**——规则不只是文档，能在 CI 挡住。对应 God ViewModel（`ChatViewModel` 5280 行）、死代码残留、`AppSettings.cs` 配置边界不清、DI 生命周期语义未确认。

### 第 3 层补位 · 桌面约定 → `microsoft/PowerToys`（138k ⭐，MIT）

GOV.UK 是 Web/移动优先，**完全没有桌面范式**（托盘、安装器、自管后端进程、单实例、自动更新）。`src/settings-ui/` 是 C# WPF 应用（`Settings.UI` / `Settings.UI.Controls` / `Settings.UI.UnitTests` / `UITest-Settings`），`src/Update/`、`src/runner/` + `src/modules/` 是分发与模块注册范式。

### 行为闭环形式化 → `statelyai/xstate`（30,098 ⭐，MIT）

唯一能**证明**闭环真的闭合的工具：状态与转移显式声明，`xstate-inspect` 可可视化——画不出转移图的环节就是漏洞，没有终态的状态就是"点了没反应"。
XState 是 TypeScript，**不直接用在 C# 后端**；取用的是建模方法：给「导入任务」与「对话生成」各写一份状态声明（`idle → running → cancelling → cancelled / succeeded / failed`），先写进契约再看代码是否跟得上。

### 可执行化 → `cucumber/gherkin`（402 ⭐，MIT）

Given/When/Then 把任务闭环写成可执行测试。后端已有 pytest、前端已有 250 项 xUnit，可直接落地。取消类测试样板：
`Given 导入进行中 When 用户取消 Then 后端任务状态 == cancelled 且无新增分块`——**该测试当前写不出来，因为假取消根本没有 cancelled 状态**，这本身即证明 FC-01 未关闭。

## Testing Decisions

1. **契约即测试**：每个功能的契约必须落为 Given/When/Then 测试，**4 个出口各至少一条**。取消出口必须断言后端状态（不能只断言 UI）。
2. **卡点矩阵扩展**：在 `docs/verification/core-chain-and-smoke.md` 增加「功能契约」一列；`scripts/smoke.ps1` 增加取消类断言（任务状态可查询且 == cancelled）。
3. **回归门不变**：`python -m pytest tests/ -q`（442 通过 / 0 失败 / 1 跳过）+ `dotnet test DocMind.Tests -v q`（250 通过 / 0 失败）+ `scripts/smoke.ps1`（FAIL = 0）。
4. **新增验收条件**：FC-01…FC-08 每条须补一条专属测试，缺测试不算关闭。

## PR 卡点规则（进入 review checklist）

**每新增或改动一个功能，PR 描述必须包含该功能的契约（前置条件 + 4 出口 + 完成判据）。缺任一项不合并。**

Review 时逐句过诊断口诀：做完用户看到什么？做失败用户下一步点哪里？取消后系统留了个什么状态？没数据时是空态还是错误？

## 诚实的空白（本规范覆盖不到，需另定）

1. **流式 LLM 交互**：SSE 逐字渲染、生成中切会话取消、来源引用角标——规范库无此范式，只能读 `open-webui/open-webui` 的交互设计（**只看设计不拷代码**）。
2. **任务取消的服务端模型**：GOV.UK 的 `file-upload` 有前端取消范式，但没有"后端继续跑"的服务端模型。此项由本规范第 0 步 + 状态机 + FC-01 自行定义。
3. **范围蔓延**：本规范是**功能级**纪律，管不了产品级范围蔓延（v1.0.1 六线并行偏离科研楔子）。后者只能由产品计划管，规范无解。
