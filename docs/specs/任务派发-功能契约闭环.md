## 任务 1 — FC-01a 导入取消粒度：单文件解析/OCR 中不响应取消

- **标题**：`[P0] 导入取消粒度：cancel_event 只在 progress 回调点检查，单文件解析/OCR 中无法中断`
- **标签**：`ready-for-agent`、`bug`
- **正文**：
  ```
  ## 现象
  后端真取消主路径已实现且正确：DELETE /v1/jobs/{job_id} 置 cancel_event 并把
  status 改为 cancelled（server/http.py:3220 附近），WPF 侧
  ImportViewModel.CancelImport()（ImportViewModel.cs:844-860）会调
  Doc2kbApiService.CancelJobAsync（Doc2kbApiService.cs:496）真发请求。

  但 ingest 工作线程只在 _check_and_update_progress 里检查取消（server/http.py:1955-1964）：

      def _check_and_update_progress(done, total, current_file=None, stage=None,
                                     stage_progress=None):
          if cancel_event.is_set():
              raise _JobCancelledError("任务已被取消")

  该回调是「文件级/阶段级」的。也就是说：一个文件正在被解析、分块、嵌入、OCR 的
  整个过程中，没有任何点会再看一眼 cancel_event。

  ## 影响
  导入 50 个文件、进行到第 2 个是 200 页扫描件（OCR，knowledge base 记录显示
  PaddleOCR 每页一次推理、无原生 batch）时，用户点取消会感觉"没反应"——
  要等当前文件整个跑完才能停。大 PDF / OCR 是最常见场景，这不是边缘情况。

  ## 关键位置
  - src/doc2mind/server/http.py:1955-1964（_check_and_update_progress）
  - src/doc2mind/core/pipeline.py（ingest_path / _ingest_parallel，取消检查点要加在这层）

  ## 建议方案
  1. 把 cancel 检查从"只依赖 progress 回调"改为"下钻层也检查"：
     在 pipeline 的文件循环、分块循环、OCR 页循环（每批 N 页）里，
     检查一个可注入的 should_cancel 回调（复用 threading.Event.is_set 的同一个对象）。
  2. 抛出与 _JobCancelledError 语义一致的异常，让 http.py:2012-2016 的既有
     cancelled 广播路径原样生效——不要另起一套状态。
  3. OCR 批粒度：按现有"每批 8 页渲染"的批次边界插入检查点，不要在每页插入
     （避免打乱 mkldnn/PIR 的实例缓存语义）。

  ## 不要碰
  - 不要改 _ingest_parallel 的写库顺序（worker 池并发解析，主线程按序串行写库
    是 SQLite 单写者语义的前提）。
  - 不要动 auto_curate_on_ingest / _spawn_background_curate。
  - 不要改 _JobCancelledError 的名字或语义。

  ## 验收标准
  - 单文件解析中点取消，能在下一个文件级/批次级检查点中断，
    job.status == "cancelled" 且 SSE 广播 {"type":"cancelled"}
  - 取消一个含大 PDF 的批次，实测中断延迟 ≤ 一个 OCR 批次（≤8 页）
  - 新增单测：解析进行中设置 cancel_event，断言 ingest_path 抛取消异常
    且该文件未写入 documents/chunks
  - 回归门全绿（见全局约束）
  ```

## 任务 2 — FC-01b 取消后残留数据不可见

- **标题**：`[P0] 取消导入后 job.results 不填充，前端无法显示"已取消，前 N 篇已导入"`
- **标签**：`ready-for-agent`、`bug`
- **正文**：
  ```
  ## 现象
  server/http.py:1993 只在 completed 路径填充结果明细：

      job.results = [IngestResultDTO(**r.__dict__) for r in summary.results]

  取消路径（server/http.py:2012-2016）直接 return，不填 results：

      if job.status == "cancelled":
          logger.info("任务已取消并终止后台线程: %s", job_id)
          _broadcast_job_event(job_id, {"type": "cancelled", "ts": _now_iso()})
          return

  ## 影响
  取消后用户看到"已取消"，但**不知道已经进了多少篇**。已入库的分块是保留的
  （可用且可搜索），可是用户无法确认残留了哪些数据。这正是功能契约规范里
  「取消出口必须显式声明残留状态」的破口。

  ## 建议方案
  1. 让 progress 回调（或下钻层）维护一个"已完成明细"列表
     （每个文件的 ingested/skipped/failed 状态），随取消一起写进 job.results。
  2. 新增 job 状态语义（或复用 cancelled + 新增 partial 标记），
     让前端能区分"完全没进"与"进了前 N 篇"。
  3. 前端 ImportViewModel 取消后展示「已取消，前 N 篇已导入，可继续搜索」。

  ## 依赖
  任务 1（同一个 agent 做，两处改动都在 pipeline 下钻层）

  ## 验收标准
  - 取消后 GET /v1/jobs/{id} 的 results 含已完成文件的明细（非空）
  - 前端取消后展示已导入篇数
  - 新增单测：导入到中途取消，断言 job.results 长度 == 已完成文件数
  - 回归门全绿
  ```

### 回归门（每次改动必过，缺一不可）

### 本轮禁止触碰

- `pipeline.py` 的 `_ingest_parallel` 写库顺序（worker 池并发解析 → 主线程按序串行写库，是 SQLite 单写者语义的前提）
- `auto_curate_on_ingest` 与 `_spawn_background_curate`
- `_JobCancelledError` 的命名与语义
- SSE 帧格式（token/done 字段完全不变，现有 pytest 流式测试是契约守护）
- `doc._openid` 相关行级安全语义
- 嵌入模型配置的双端同步逻辑（`%APPDATA%\doc2mind\config.toml` 与 WPF `appsettings.json` 必须同时改；WPF 启动时无条件注入 `DOC2MIND_EMBED_MODEL`，优先级高于 config.toml）

### 已知陷阱（改动前读一遍）

- 修改 `src/doc2mind/core/pipeline.py` 前先查知识库「DocMind 导入性能优化与嵌入模型升级经验（2026-09）」——该文件近期经过大规模并行化重构，多处非显而易见的约束。
- XAML 全局替换后必须 `git diff` 复查（曾误伤标题栏/状态栏合法元素）。
- Windows bash 下 `sed` 会把 CRLF 转 LF，且易损坏 UTF-8 中文，宜用 Python 字节级处理。
- 删死代码前全库 grep 零引用确认。
- 行尾不强制：`docs/specs/` 下既有 CRLF 也有 LF，`.gitattributes` 为 `* text=auto`，git 自动归一，无需手动统一。

### 范围红线

本轮**不做**：范围蔓延治理（v1.0.1 六线并行偏离科研楔子）、God ViewModel 进一步拆分（`ChatViewModel` 已用 partial class 拆为 5 文件）、前端后端解析逻辑统一（PPT 切片双份实现）。这些是产品级或架构级议题，不属本轮功能契约闭环整改。
